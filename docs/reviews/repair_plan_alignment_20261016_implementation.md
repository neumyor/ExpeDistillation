## 逐条发现

### 发现 1：阻断 — 契约 §6 的 pipeline_log key 与 audit_live_run manifest 模式分派规定，修复方案 R9 没有写出

**证据**

契约 §6 明确规定："`pipeline_log` 行 key 仍为 `"stage"`（消费者兼容），值 = `p00:freeze`、之后 `pNN:<局部名>`"；"`audit_live_run` 改读相位目录与 `pNN` 标签、manifest 模式分派从 `config.methods.acceptance` 改为冻结序列判型"。

修复方案 R9 的字段表列出了执行相位与学习相位的配置字段（`kind`、`tasks`、`delivery`、`execution`、`compare`、`acceptance`、`evidence`、`author`、`curate`），加载期检查七条，以及"`--until-phase N` 取代 `--until-stage`"；R10 写了"`scripts/audit/audit_live_run.py` 读取相位目录与 `pNN` 标签"。但 R9 和 R10 都没有写"`pipeline_log` 行 key 仍为 `"stage"`"这条兼容性规定，也没有写"manifest 模式分派从 `config.methods.acceptance` 改为冻结序列判型"的具体实现要求。

**问题**

`pipeline_log` key 的向后兼容性是消费者行为的硬约束，实现代理需要明确知道这一点。"manifest 模式分派"的改法（从读 `config.methods.acceptance` 改为读冻结序列判型）是 `audit_live_run.py` 的具体逻辑变更，不写进方案则 W3-B 代理无法正确实现。

**修改建议**

在 R9 验收方式里补一条："`pipeline_log` 行 key 保持 `"stage"`，值格式为 `pNN:<局部名>`，消费方兼容性测试通过"；在 R10 的 `audit_live_run` 条目里补："manifest 模式分派改为从冻结序列判型（含 A 相位则为 exam 方式，否则为 live_run 方式），而不再读 `config.methods.acceptance`"。

### 发现 2：阻断 — 契约 §4 加载期检查第五条（roles 有效）与修复方案 R9 第八条之间的对应关系未写出

**问题**

修复方案新增了一条契约里没有的检查（`invalid_redispatch_limit`），这是合理的新增，但方案没有写明这是新增检查而不是替代了某条原有检查。读者无法确认契约的五条检查是否全部被接管。

**修改建议**

在 R9 验收方式里注明："检查条目七、八是修复方案新增；契约原五条与方案七条的对应关系：契约一对应方案一到三，契约二对应方案四，契约三对应方案五，契约四对应方案六，契约五对应方案八。"
