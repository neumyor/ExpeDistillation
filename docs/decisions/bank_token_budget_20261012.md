日期：2026-10-12
一句话：`bank_token_budget` 的取值从试点占位值 4096 改为按库实际规模设定的 96000，
三个 benchmark 在各自实验启动前统一预注册；该预算的角色是"上下文溢出安全阀"，
不是"压缩目标"。

## 背景（时间线）

- `bank_token_budget: 4096` 沿自试点配置（pilot 的库只有 1 条 skill）。
- TB21 正式 run（runs/tb21_full_20261011_2242）阶段 4 通过验收 119 条 skill；
  阶段 5 实测：102 条成员 ≈ **80,145 估算 token**，为预算的 ~20 倍。
- MERGE prompt 的合同是"一条建议都不丢"（prompts/curate.py），实测 10 次保留
  合并的压缩率 ≈ 0.98（10 组 kept 只省 ~1.5k token）——**"多合并几轮压进预算"这条路
  数学上不存在**；即使 3 轮全部跑满，阶段 5 必然以 ConfigError 停机等人工决定
  （README 阶段 5 的设计出口）。
- 五份独立设计评审（2026-10-12，见 log.md）独立得出同一结论，并指出排期前提
  "阶段 5 已近尾声"不成立。

## 决定与理由

- `bank_token_budget` 的本职是**防注入块超出模型上下文**的安全阀，不是库大小的
  方法学控制。试点值 4096 对百条量级的库没有意义。
- TB 采用新 run 目录（`runs/tb21_full_v2_*`）+ 新配置（`configs/experiments/tb21_full_v2.yaml`，
  预算 96000）；阶段 0–4 的全部产物按确定性 ID 从旧 run 复制（零模型调用，复制后
  `--until-stage 4` 干跑验证零调用），阶段 5 从当前成员集继续。
- ALFWorld / SearchQA 的预算在**各自实验启动前**同步预注册为 96000（两个实验
  尚未开始，此为预注册而非事后调整；三个 benchmark 口径统一）。
- 数值依据：当前库 80,145 估算 token，96000 给后续合并轮次留 20% 余量；
  102 条 skill 的注入块在 TB 沙箱代理（弱模型，128k 上下文）内可容纳，
  阶段 6 首个 trial 作为实测冒烟（若真实 token 计数显著超预期——估算对散文
  约 ±20%——按外层 AGENTS.md 先停下核对再放量）。
- 附带：借此窗口，阶段 5 的并行化新代码（保语义波次并行，五份评审收敛方案，
  见 curation.py 模块 docstring）与新预算同时在新 run 生效——三个 benchmark
  统一用新代码，"TB 旧策略、其余新策略"的方法学混杂问题随之消失。

## 与冻结协议的关系

`bank_token_budget` 冻结在各 run 的 manifest 中；旧 run（4096）保持原样作废归档，
新 run 以新值冻结。这是"由人决定"的设计出口的第一次行使，不是协议中途修改。

## 风险与对策

- **弱模型上下文溢出**（102 条 ≈ 80k 估算 ≈ 100k±20% 真实 token）：阶段 6 首个
  trial 冒烟核查（弱模型上下文 128k；超限则停下重新决策，绝不批量放量）。
- **稀释效应**（README 已知风险 3：多 skill 互相冲突/稀释）：这正是实验要测量
  的对象；102 条是流水线按设计跑出的真实产物，交给阶段 6 让数据说话。
