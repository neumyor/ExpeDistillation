## 背景

实验三要比较"切成子任务归因"与"整条轨迹为单位"，实验四要比较"演化触发条件"与"只演化正文"等
几种安排。现有方法没有办法把这些因素单独关掉，所以需要若干只改变一个因素的开关。开关的缺省值
复现原方法，旧配置的行为不变，因此不升配置版本（AGENTS.md 8.9：带缺省值的可选参数）。

## 触发条件与正文的划分

读者在技能目录里先看到的是一行描述：`summary` 加 `[When to use]`。打开卡片后才看到
`[Steps]` 和 `[Do not use when]`。划分如下：

| 部分 | 内容 | 读者何时看到 |
|---|---|---|
| 触发条件 | `summary` + `[When to use]` | 打开之前，决定要不要打开 |
| 正文 | `[Steps]` + `[Do not use when]` | 打开之后，决定怎么做 |

`[Do not use when]` 归正文，因为目录里不显示它。

## 决定

1. **`revise_scope`（`both` / `body` / `trigger`）。** 限制考试路径的改写能改哪一部分。两层保证：
   提示词里告知改写模型它的范围（`REVISION_SCOPE_BODY`、`REVISION_SCOPE_TRIGGER`，通过 REWRITE 的
   `{scope_section}` 槽位）；模型输出之后再按分节拼接（`core/skill_sections.py`、
   `blocks/author.py::enforce_scope`），范围之外的部分逐字节取自当前版本。拼接让消融成立，
   与模型是否听话无关。
   - 输出缺少某个分节：`ModelOutputError`，沿用改写预算的重试。
   - 当前版本不是三节结构：`CodeBugError`。
   - 实战路径不支持：配置了会在学习相位开始时报配置错误，因为静默忽略会让结果看起来像做了消融。
2. **`new_skills`（缺省 `true`）。** 关掉时 `trial_level` 聚合出的跨任务新技能需求照常写进
   `new_skill_requirements.jsonl`，回执为 `not_written_new_skills_off`，不调用写作。
   `revise_scope` 不约束需求：新技能没有"当前版本"可冻结。因此触发条件消融的各臂必须同时关掉
   `new_skills`，否则新技能的触发条件由弱模型的失败证据重新写出，等于在"触发条件不演化"的臂里
   开了一条触发条件演化的通道。
3. **`accept_new`（缺省 `false`）。** P02 add 写出的技能直接成为已接受成员。没有它，一个只有
   `baseline → learn_add → test` 的序列交付的是空库（终测只交付已接受成员）。这个开关让"没有演化的
   教师技能"和"没有检验的方法消融"都能直接评测。两条 add 路径（逐任务、按触发族聚类）都在
   provenance 账本里写 `cause: add`，开关据此翻转状态，与路径无关。
4. **`K: 1`。** 切段每条轨迹只出一段，整条轨迹成为学习单元：写作的素材是整条轨迹，考试的切点
   是任务起点（provenance 的场景步号为 0），审阅按该技能自己的考题进行（审阅单位已经是整张答卷，
   与 K 无关）。不需要新代码，只需要确认全链路在 K=1 下成立：D7 拒绝超过 K 的切法并走重切预算，
   一段覆盖全轨迹时通过（见 `tests/unit/methods/review/test_segmentation.py`）。

## 实验四的臂

| 臂 | `revise_scope` | `new_skills` | 序列 |
|---|---|---|---|
| a0 不演化 | 无学习相位 | 无 | baseline, learn_add, test（`accept_new: true`） |
| a1 只演化正文 | `body` | `false` | 七相位 |
| a2 只演化触发条件 | `trigger` | `false` | 七相位 |
| a3 联合，不写新技能 | `both` | `false` | 七相位 |
| 完整方法（e1） | `both` | `true` | 七相位 |
| joint9 / staged9 | 两轮均 `both` / 第一轮 `body` 第二轮 `trigger` | 缺省 | 九相位，最后一个学习相位不改写 |

a1、a2、a3 之间只差 `revise_scope`；a3 与完整方法之间只差 `new_skills`。

## 没有实现的

**"最后一个学习相位之后一次性重写触发条件"。** 设想过把它作为触发条件消融的第五个臂（正文在循环里演化，
触发条件在循环外一次性补）。放弃，原因是证据：最后一个学习相位里留下来的技能都是考试通过的，
没有"触发失败"的证据可用来重写；用没通过的技能的证据去重写再直接接受，等于没经检验就入库，
与框架"终测只交付检验过的技能"相矛盾。同一个问题改为用纯配置的"分阶段"对照回答：
九个相位的序列里，第一轮改写只改正文、第二轮改写只改触发条件，每轮之后各有一次考试检验；对照是同一序列
里两轮都不受限的联合改写。两者的配置差只在两个 `revise_scope`。

## 已知边界

- `revise_scope` 只约束改写，不约束新技能的初稿：P02 写出的技能的触发条件始终来自强模型的初稿，
  "只演化正文"臂的触发条件因此是强模型写的、未经弱模型反馈修正的。这正是该臂要代表的状态。
- 整条轨迹单元在 TB 上输入很长（轨迹最长可到几百步）。`author` 与 `rewriter` 角色已要求
  512K 输入预算；若仍然超限，该单元按既有规则记为模型输出失败，不会静默丢弃。
- 新提示词（两个范围提示）改变所有 run 的提示词名称集合，旧 run 不能在新代码上续跑。
