对应 log.md 条目：2026-10-11（D8 泄题审计换成 LLM 判官）。

## 背景

机械审计（`extract_specifics` 收集引号段、数字、文件名式 token、全大写缩写，
`leak_audit` 按"命中比例 ≤ `leak_threshold`"判通过）在真实 pilot 上系统性
误报，杀掉了合法 skill：

1. **没有词边界的子串匹配**：缩写 "AI" 命中 "contAIn" 一类词内子串；
2. **引号内容一律视为受保护实体**：协议 token 被当成泄题材料 —— 被误杀的
   skill 里出现的是动作名 "Finish" 和环境反馈串 "answer is incorrect."，它们
   来自任务协议本身，任何照协议执行的 skill 都会包含，与本题答案无关；
3. **比例阈值无语义**：命中几个"具体值"和是否真的泄露答案没有稳定关系。

误报的代价是双向的：直接杀掉合法 skill（该版作废、烧掉一轮改写），而降低
阈值又会放过真泄露。重合度是句法信号，泄题是语义判断，机械规则两头都不对。

## 决定：换成 LLM 判官

`blocks/audit.py` 的 `audit_leak`：一次 `call_model`（prompt
`LEAK_AUDIT_JUDGE`，output_json），输入 skill 正文、考题、参考答案，输出
`{"leaked": true|false, "reason": "..."}`。判官规则写进 prompt：

- **判泄露**：skill 包含、平凡改写或直接揭示受保护答案材料（参考答案本身，
  以及考题中属于答案的具体实体：名字、数值、文件名）；
- **不判泄露**：对任何同类任务都有帮助的通用方法建议，即使恰好适用于这道
  考题；协议词、动作名、环境反馈串一律不算泄露（修掉第 2 类误报）；
- **reason 永不复述参考答案**（见下）。

模型由调用方传入（新角色 `auditor`，默认取强模型，可在配置角色表里覆盖），
积木本身不选模型。`leaked` 是闭集校验（必须是 JSON 布尔），`reason` 必须是
非空字符串，违反即 `ModelOutputError`，绝不猜。

## 非确定性：首判为准（first verdict sticks）

LLM 判官不可复现，同一个 (skill, version) 问两次可能得到不同判决。K4 的续跑
等式（"任何一处崩溃后续跑，结果都与一次跑完相同"）因此不能靠重问保证，只能
靠落盘回放：

- 每个判决追加一行进 `stage4_acceptance/leak_verdicts.jsonl`，每
  (skill_id, skill_version) 恰好一行，**落盘发生在本轮依据判决行动之前**；
- 续跑（以及同一 run 内改写预算耗尽后对同版本的下一轮）先查表：查到就用，
  **绝不再问判官**；
- 崩在"判决落盘之后、本轮继续之前"→ 续跑用盘上判决，与一次跑完相同；
  崩在落盘之前 → 判决视作在途，续跑重问（与 K3 在途作答同待遇）。

## 两个留给我定的设计选择

1. **旧失败账本 `leak_audits.jsonl` 并入新判决账本**（不再保留两个文件）。
   理由：两者按同一个键 (skill, version) 记同一件事，双账本必然出现漂移
   （有判决行无失败行、或反之）；`leaked=true` 的判决行本身就是作废簿记，
   单一文件是唯一事实来源，续跑和审计都只读它。写入次数也从"每轮可能一行"
   降到"每版本恰一行"。
2. **判官格式错误沿 K3 的处置传播**：`audit_leak` 的 `ModelOutputError`
   （`leaked`/`reason` 违反契约，或 call_model 修复预算耗尽）在 K4 里不设
   组合级重试预算，直接抛给阶段 4 的单元处置——终态丢弃
   （`discard_reason = model_output_error`）。理由：与 K3 修复预算耗尽的处置
   完全同类（同一个异常、同一个终态），审计发生在带 skill 作答之前、没有
   可复用的中间产物可续，而持续违反输出契约的判官在后续轮次只会重复同样的
   坏调用、白烧 token。续跑等式两边一致：崩溃前判决未落盘 → 该 skill 保持
   pending，续跑重问；丢弃已落盘 → 终态，续跑不再进入。

## reason 永不复述答案的约束

泄露判决的 reason 会作为该版作废后 G6 改写的错误描述（`_VOID_NOTE` +
reason），而 G6 按设计**看不到参考答案**（README 阶段 4 的三条约束之一）。
若 reason 复述答案，泄题审计就成了把答案递给改写者的通道——被作废的正是
"含答案"，改写上下文里却带着答案。所以 prompt 明确要求 reason 只说泄露
材料的**种类**（如"考题情境里的一个具体数值"），不说材料本身。

## 移除的机械规则

- `leak_threshold` 配置字段与 `[0,1]` 校验：一并删除。`from_dict` 丢弃
  未知键，**旧配置文件（含 `leak_threshold: 0.3`）仍能加载**，多余键被
  静默忽略；已启动 run 的 manifest 不受影响（改 prompt 即新实验，本就是
  新 run）。
- `extract_specifics` / `leak_audit` / `leak_audits.jsonl`：删除（账本并入
  见上）。
- 阶段 4 之外唯一引用 `ctx.config.leak_threshold` 的是阶段 5 对
  `curate_bank` 的透传（该参数在 K5 里本就未使用）；透传处改为常量占位，
  K5 签名本身未动。

## 已知局限：判官自审

auditor 默认取强模型，而写 skill（G2）与改写（G6）的默认也是强模型：
**判官在审自己写的 skill**。同一个模型既当作者又当审计员，可能对自己的
措辞风格系统性宽大。要打破这个共谋，把配置角色表里的 `auditor` 换成另一个
强模型即可（角色表本来就是为按角色覆盖而设）。这是当前流水线所有判分类
角色（judge 等）共有的结构限制，不是 auditor 独有；在 README 的 D8 行与
阶段 4 说明里如实标注。
