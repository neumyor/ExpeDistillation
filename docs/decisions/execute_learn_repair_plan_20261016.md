## 0. 阅读前的术语说明

这份文档反复使用下面几个词，第一次出现的地方也会解释，这里先集中说明一遍。

**相位**：方法序列里的一步。整个方法是一串相位，每个相位要么是执行相位，要么是学习相位。例如考试方法的序列是 D、L、A、L、A、L、A、L、C，共九个相位，其中 L 是学习相位，D、A、C 是执行相位。

**执行相位**：技能库加任务加模型，跑出运行记录和验收报告。

**学习相位**：验收报告加运行记录加旧技能库，算出新技能库。

**执行单元**：一道题，加上给这道题注入的技能。技能可以是一条、几条，也可以一条都不注入。

**对照单元**：与某个执行单元同样的题目、不注入任何技能的那个单元。它是"注入技能到底有没有用处"的参照物。

**注入块**：把技能渲染成文本之后的那段字符串，是真正放进模型输入里的内容。同一个技能在不同的渲染方式下会产生不同的注入块，所以跳过判断要同时比对技能列表和注入块的字节。

**对象仓**：存放轨迹、技能、考题、答卷、分段这五类对象文件的目录。这五个目录属于整个 run，被所有相位共用，目录名保持现状不变。Run 是一次完整的实验执行过程，对应磁盘上的一个带锁目录。

**跳过键**：一个单元的身份标识。程序再次启动时，用这个标识判断该单元是否已经完成，已完成就跳过。本次改动要求跳过行为与现在完全一致。

**manifest**：运行开始时写入磁盘的配置快照文件，记录任务摘要、prompt 摘要、模型选项等关键信息。程序每次启动时把当前配置与 manifest 逐字段比对，不一致则拒绝继续，防止在配置变化后续跑到错误状态。

**shortfall**：运行结束时某些单元既没有成功也没有标记为彻底失败的情形。`composites/shortfall.py` 记录这类"欠账"并在下次启动时作为补充任务重新派发。

**金夹具（golden fixture）**：`tests/fixtures/golden_semantic_baseline/` 目录下存放的归档基线数据，是一次预先跑出并人工审定过的完整运行结果。语义等价检查工具（E1–E6）把每次新运行与这份归档逐项比对。金夹具里的全部场景都是"全部接受、零丢弃"的，所以 E2 的丢弃分支在金夹具上永远不会触发，丢弃场景由单独的场景测试覆盖。

**K4 与 K6**：代码里对 composites 层两个编排函数的称呼，来自实施契约的编号体系。K4 是考试方法里的答题判卷编排（`composites/exam_once.py` 的核心流程），K6 是实战方法里的执行编排（`composites/live_acceptance.py` 的核心流程）。本次改动把这两个编排按职责拆开，它们原来的逻辑是被改造的主要对象。

**G6、G10、G11**：实施契约里对编排步骤的编号，沿用至今。G6 是考试改写步骤，G10 是实战归因步骤，G11 是实战改写步骤。这三个编号在本文里只出现在说明它们与边界定稿分歧的地方，实施时统一改用修复项编号 R6。

**差距编号 G 与修复项编号 R**：G1 到 G11 是代码里待修复的问题，R0 到 R10 是把这些问题修好所需的工作项。每个修复项的标题后面写明它消除哪几个差距。

**语义等价与 E1–E6**：`tests/golden/semantics.py` 里有一套检查工具，它把一次完整运行产生的文件按照六种视角汇总，与归档的旧版本结果逐项比较。六种视角记作 E1 到 E6，含义见 §4.3。这套工具用来证明改动之后系统的行为没有意外变化。

**live**：本文中作为形容词使用时，指"实战"方法（live_run），即让模型在真实任务上执行并按表现更新技能库的方法，有别于考试方法（exam）。

## 2. 待修复的问题清单（G1–G11）

「位置」一列给出 `c6a9fb8` 上的实际代码位置，便于逐一核对。

### G1 没有验收模块，判定工作分散在五处

**问题**：没有任何一个模块负责回答"这一次运行算不算成功"。这项工作被拆散写在五个地方，分别是：

1. `benchmarks/tb/plugin.py` 的 `classify_result` 函数：判定伪零分、按 `reward > 0` 决定成功或失败、把模型异常与 tmux 报错算作失败、把其余情况算作基础设施错误；
2. `composites/batch_execute.py:354`：遇到基础设施错误时触发重试；
3. `composites/exam_once.py:270` 与 `:298`：作答与判卷写在同一个函数 `exam_once` 里面，判卷结果直接写进 Attempt 对象的 `judge_verdict` 字段；
4. `composites/acceptance.py:290`：泄题判定与 `accept_skill`；
5. `composites/live_acceptance.py`：verdicts 账本、G10 归因，以及五处丢弃技能的调用。

**为什么是问题**：判定逻辑分散之后，改变判定标准要同时改五个地方，而且执行、验收、决策三种不同性质的判断混在同一条代码路径上，职责不清。

### G2 执行模块自己下定论

**问题**：`benchmarks/base.py:53` 定义 `RUN_STATUSES = ("success", "failure", "infra_error")`，只有三个取值。这套取值无法表达"对错未知"（benchmark 没有判分器时），也无法表达"这次运行不算数"。另外 `composites/exam_once.py:270` 的作答与 `:298` 的判卷写在同一个函数里。

**为什么是问题**：执行模块的职责是把不同 benchmark 的运行结果整理成统一格式，它无法只记录事实而不下结论。

### G3 比较工作写在执行阶段，决策模块没有统一入口

**问题**：`stages/stage6_test.py:195` 的 `_delta` 计算带技能与裸跑的成绩差值，`:330` 与 `:357` 决定对照数据来自 `stage1_reuse`（复用第一阶段的结果）还是 `fresh_bare_run`（本阶段现跑）。`composites/decision.py` 里有 12 个公开函数，分成 `exam_*` 与 `live_*` 两套，没有"本轮报告、对照报告、当前技能库、后面还剩几次检验，得出任务清单"这样一个统一入口。

**为什么是问题**：边界定稿 §3 第 1 条规定比较工作归决策模块。现在比较写在执行阶段内部，决策模块无法独立控制比较口径。

### G4 执行阶段直接修改技能库

**问题**：`composites/live_acceptance.py` 有五处调用 `discard_skill` 丢弃技能，位置是 `:1003`、`:1084`、`:1217`、`:1276`、`:1325`，丢弃原因包含 `LIVE_REVISION_DELETED`、`MODEL_OUTPUT_ERROR`、`LIVE_NO_IMPROVEMENT`。`composites/acceptance.py:290` 的 `accept_skill` 同理。

**为什么是问题**：边界定稿规定技能库的变更只在决策模块发生。现在变更发生在执行与验收内部，难以审计也难以为每一处变更找到依据。

### G5 交付的五个驱动有三种不同的函数签名

**问题**：

- `delivery/none.py:19` 与 `delivery/whole_bank.py:19` 接收 `(ctx, params, bank, ...)`；
- `delivery/per_skill.py:22` 接收 `(..., skill)`，一次只处理一条技能；
- `delivery/group_by_task.py:25` 接收 `(..., store, benchmark)`，返回一个闭包；
- `delivery/retrieval.py:54` 接收 `(..., bank)`，也返回闭包，另有独立的 `:97 write_audit` 负责写审计记录。

**为什么是问题**：五种交付方式要用五种方式调用，谁调用谁就得记住这一种的特殊签名。边界定稿 §2.1 要求交付的输出统一是执行单元清单。

### G6 报告有三种形状，并且跨模块读取私有函数

**问题**：`composites/reports.py:44` 只导出 `baseline_report`、`exam_report`、`live_report` 三个函数，各自返回不同结构。同一个文件里有 6 处调用 `live_acceptance` 的私有函数，还有 6 个从 `acceptance` 导入的私有名称。

**为什么是问题**：边界定稿 §2.3 要求只有一份验收报告，决策模块读这一份。写决策规则时要按报告种类分别处理三种结构。跨模块读取私有函数意味着模块边界没有被遵守，改动其中一个模块会意外破坏另一个。

### G7 找证据只有一个参数类，没有实现

**问题**：`methods/evidence/__init__.py` 共 34 行，只定义 `SegmentationParams` 参数类，没有驱动。live 方法的归因步骤 G10 写在 `live_acceptance.py` 里面，并且直接产出保留、修改、删除三种动作的计划。

**为什么是问题**：边界定稿 §2.5 规定找证据只报告事实，动作由决策模块决定。现在找证据这一步自己就在决定动作。

### G8 写作只有一个参数类，没有实现

**问题**：`methods/author/__init__.py` 共 23 行，只定义 `AuthoringParams`，里面还留着旧版配置的 `exams` 开关。改写编排 G6 与 G11 仍然按报告种类分发，写在 K4 与 K6 内部。

**为什么是问题**：边界定稿 §2.6 规定写作只依据证据包落笔，不区分证据来自考试还是实战。按报告种类分发写作流程与这条规定相违。

### G9 技能库产物不按相位产生

**问题**：新技能库目前由阶段 5 整理、阶段 6 隐含读取。每个学习相位结束时不会产生一份可以单独加载的技能库。

**为什么是问题**：边界定稿规定学习相位的输出是新技能库，下一个执行相位要能直接加载它。现在没有这个产物，相位之间的衔接只能靠读取中间状态，无法确认新技能库是否被正确传递。

### G10 相位语义写在代码里，注册表有两套键

**问题**：`stages/pipeline.py:61` 的 `STAGE_NAMES` 在代码里写死六个阶段名。`methods/registry.py:45` 的 `_ENTRIES` 共 13 项，旧槽位键 `(segmentation, llm)`、`(authoring, distill_diagnose)`、`(acceptance, exam)`、`(acceptance, live_run)` 与 M3 新增的族键 `(evidence, segment)`、`(author, distill_diagnose)` 同时存在。

**为什么是问题**：相位序列要能通过配置自由组合，写在代码里的阶段名使组合方式固定。注册表里两套键并存，按名查找时无法确定该用哪一套。

### G11 配置仍是五个槽位，命令行界面仍按阶段编号

**问题**：`core/config.py:82` 的 `METHOD_SLOTS`、`:89` 的 `METHOD_DEFAULTS`、`:204` 的 `_validate_methods` 定义了五个固定槽位。`cli.py:173` 使用 `until_stage` 参数。

**为什么是问题**：边界定稿要求用 `sequence` 与 `phases` 描述方法，支持任意相位组合。五个槽位只能表达固定的流水线。命令行界面按阶段编号停止，与相位序列不对应。

## 4. 硬约束

任何一步工作都不得违反以下规定。

### 4.1 分层与依赖

1. **九层向下依赖**：core(0) ← infra、prompts、inject(1) ← llm(2) ← benchmarks(3) ← blocks(4) ← composites(5) ← methods(6) ← stages(7) ← cli(8)。上层可以调用下层，下层不得调用上层。`tests/test_layering.py` 全程通过。
2. **composites 层不得 import methods 层**。决策逻辑写在 composites 层，可选做法写在 methods 层，流程编排写在 stages 层。
3. **methods 目录下各模块互不 import**，注册表是唯一的调用接缝。
4. `gen_exam` 与 `audit_leak` 是 blocks 层的模型积木，只移动调用它们的位置，函数本身不动。

### 4.2 续跑契约

5. 每完成一个单元立刻写入磁盘，写入方式是先写临时文件再改名，保证不会写到一半；程序再次启动时按确定 ID 跳过已完成的单元；终态先写，账本行作为回执后写；启动时把 manifest 与当前配置逐字段比对；run 目录加排他锁。
6. **五个对象仓保持 run 级、全部相位共享、目录名不变**（trajectories、subtasks、skills、exams、attempts 对应的目录）。相位目录只存放该相位自己的账本与 summary 文件。
7. **跳过使用的键就是现行的续跑键**。边界定稿 §4.3 第 1 条要求"题目与注入的技能都没有变化的单元沿用上一次的验收结果"，这一条需要的判定键单独定义，与续跑键并存。
8. 异常分类（四类）与恢复机制的语义不变，包括 shortfall 记录、修复预算、相位结束时抛出错误、退出码。

### 4.3 语义等价

9. `tests/golden/semantics.py` 里的 E1–E6 是验收工具。每一步改动之后都要对归档基线保持等价，或者逐处披露差异并说明理由。
10. 六条准则同时成立：

| 编号 | 比较内容 |
|---|---|
| E1 | 最终技能库的每一行，按多重集比较 |
| E2 | 逐技能与逐组的终态以及 discard_reason |
| E3 | C 相位的 summary 字段，以及 retrieval_audit 审计行 |
| E4 | 模型调用的多重集，即每一次调用的角色、prompt 名、渲染后的请求文本 |
| E5 | 8 种组合乘以 3 种崩溃续跑变体的等价性 |
| E6 | live 测量账本逐行比较。其中 verdicts 部分保持逐行等价，attributions 部分按 R6 的新形状披露差异 |

11. **检查工具的覆盖范围**：E1–E6 不比较运行记录本身的字段。金夹具全部是"全部接受、零丢弃"的结果，E2 的丢弃分支在金夹具上恒为空真。丢弃分支由 R1 附带的场景测试约束。

### 4.4 有意改变的行为

以下三处行为按边界定稿需要改变，改变之前先登记，改完之后在验收时按预期差异核对。

12. **基础设施错误的重试位置改变**：现状是 `benchmarks/tb/plugin.py` 的 `classify_result` 把 tmux 报错、模型异常归为 infra_error，`batch_execute.py:354` 据此重试。改动之后，这类"拿到了结果但运行已经损坏"的情形由验收判定为无效，交给相位驱动重新派发，无效的运行不计入分母。模型调用次数的账目（E4）与续跑期望（E5）相应变化。
13. **改写没有产出新版本时的处置改变**：现状是改写之后注入内容与冻结行相同时直接丢弃技能，丢弃原因是 `LIVE_NO_IMPROVEMENT`。改动之后视为没有变化，保留技能，不重新测量。
14. **对照全部正确时的处置改变**：现状是照常执行带技能的运行。改动之后跳过这次运行，在报告中标注"未跑：对照已全对"，决策据此得出"无提升空间"。这一条只在比较规则属于严格提高一类时适用。

### 4.5 测试结果不流进学习

15. 边界定稿 §3.9 原文：测试结果不流进学习。C 相位的报告只进入最终成绩，"带技能库比裸跑提升多少"由最终汇总计算，不经过决策。

**运行记录**（执行模块产出，每次运行产生一条）

3. **两条逐技能删除路径的归属**：改写流程内的删除（丢弃原因 `LIVE_REVISION_DELETED`）归写作；归因预算耗尽导致的整组放弃归决策。

**验收方式**

- G10 的输出里不再有保留、修改、删除三种动作。
- 修改没有产出新版本时按 R3 的配套规则处理，场景测试通过。
- 改写预算耗尽的场景测试通过。

### R7 整理与逐相位技能库（消除 G9）

**要做什么**

1. 每个学习相位结束产生一份技能库产物。新技能库等于旧库去掉删除的、替换为修改后的、加上新增的。
2. 整理只做合并、归类、控制总长度。可用的方式有两种：`agentbrew`（带 `merge_check` 参数，取值为 `exam` 或 `none`）与 `none`（原样入库，不做整理）。

**验收方式**

- E1 的最终技能库行多重集不变。

### R8 相位语义与注册表换键（消除 G10）

**要做什么**

1. 相位角色由配置显式声明，不再根据结构推断。代码里不出现"attempts 等于 2 所以是基线相位"这类判断。

**验收方式**：注册表条目从 13 项降到五个族的全部条目；`test_layering` 通过。

### R9 配置 v4、相位驱动、命令行界面（消除 G11）

**要做什么**

1. 配置顶层使用 `sequence` 与 `phases`。删除 `METHOD_SLOTS`、`METHOD_DEFAULTS`、`_validate_methods`。
2. 执行相位的配置字段：

| 字段 | 取值 |
|---|---|
| `kind` | `execute` |
| `tasks` | `train` 或 `test` |
| `delivery` | 嵌套的交付参数 |
| `execution` | 嵌套的执行参数，`name` 取 `real` 或 `exam` |
| `compare` | 可选。形状为 `{against: <更早出现的相位名，或 fresh_bare>, rule: <具名规则，可选>}` |
| `acceptance` | 验收的具名判定规则，对应 C11 |

单臂的 `real` 相位可以带 `n_attempts` 与 `max_injection_tokens`。双臂相位（D 相位）禁止携带 `n_attempts`，两边的深度由全局的 `n_attempts_strong` 与 `n_attempts_weak` 决定。

3. 学习相位的配置字段：

| 字段 | 取值 |
|---|---|
| `kind` | `learn` |
| `evidence` | 切段参数 K 与 retry_limit |
| `author` | 写作方法名 |
| `curate` | `agentbrew`（带 `merge_check`、`token_budget`、`rounds`）或 `none`（带 `token_budget`） |

整理只在序列末位的学习相位执行，由驱动按序列位置分支。

4. 配置加载时执行这些检查，检查不通过就直接报错，不进入运行：

   - 序列非空，且序列里的名字都在 `phases` 里；
   - 相位局部名的字符集受限，这一点要明确写出；
   - 相位的字段集合与 `kind` 匹配；
   - `compare.against` 引用的是序列中更早出现的相位名，或者恰好是 `fresh_bare`；
   - 单臂 `real` 相位的 `n_attempts` 不超过对照相位的弱模型运行次数；
   - `merge_check: exam` 要求序列中含有考试执行相位；
   - `invalid_redispatch_limit`（无效单元重新派发的次数上限）为正整数；
   - 模型角色有效。

5. 相位驱动取代 `stage1` 到 `stage6`：`stages/phase_execute.py` 负责交付、执行、验收；`stages/phase_learn.py` 负责决策、找证据、写作、整理。`stage0_freeze.py` 沿用。
6. 执行相位内部的顺序固定为：先跑对照单元，验收对照单元，再决定是否需要跑带技能的单元。这个顺序服务 §4.4 第 14 条。无效单元的重新派发在相位驱动内完成，次数用尽之后该单元留作空缺，并记为 `invalid_redispatch_exhausted`。
7. `--until-phase N` 取代 `--until-stage`。N 是序列的 0 基索引，freeze 恒跑。标签从冻结序列派生，形式为 `pNN:<局部名>`。

**验收方式**

- E5 的 8 种组合乘以 3 种崩溃续跑变体全部等价。
- 7 份旧配置经 `upgrade_v3_config` 转换之后逐份人工审定，包括 4 份 `*_v3.yaml` 与 3 份 `*_v2_v3.yaml`。

## 7. 评审与提交纪律

1. **每个波次结束后启动三路评审**（只读，可并行）：A 关注正确性与行为等价，B 关注简洁与避免过度设计，C 关注迁移与续跑。只审该波次的改动与该波次的验收证据。
2. **Wave 0 的评审最严格**：它的错误会被 Wave 1 的六个代理各自放大一遍。
3. 每个代理只在 ExpeDistillation-MM 内工作；`test_layering` 与 ruff 检查通过之后才提交；不推送；完成后追加自己的 `log.md` 段落。
4. 提交的次数：Wave 0 两次；Wave 1 每个代理各一次（六个提交，便于单独回退某个模块）；Wave 1B 一次；Wave 2 三次；Wave 3 三次；Wave 4 一次。
5. 测试命令使用仓库的虚拟环境解释器 `.venv/bin/python -m pytest`。
6. **修复全部完成之前不启动任何正式 run**（AGENTS.md 第一节：不在未经充分验证的代码上跑长任务）。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| Wave 0 的机械拆分改变语义 | 提交一的验收方式是产物逐字节无差异；出现差异时先回退再排查 |
| 运行状态词汇迁移波及面广 | 单独排在 Wave 1B 的串行窗口，一次提交完成，便于一次定位回归 |
| Wave 1 六个代理对报告字段的理解不一致 | W1-A 先核对并广播形状；其余五个代理在形状确认之前只写框架 |
| W1-A 进度落后拖住整波 | 验收处于关键路径，优先投入；其余五项先行完成，只在最终接报告时等待 |
| 并行过程中出现重复实现（例如两个代理都实现技能库产物） | 逐文件归属表是硬约束；每个波次只在清单内的文件上工作，需要改动清单外的文件时先向该波次的协调者报备并由其指派 |
| 相位驱动的代码量过大（历史实现曾达 1019 行） | W2-A 与 W2-B 各自只写自己那一个驱动；超过 400 行的驱动先拆分再写 |
| golden 重新生成的工作量被低估 | 单独作为 Wave 4，由一个代理完成 |
| 旧 run 的续跑中断 | 对象仓保持 run 级共享、目录名不变；E5 的崩溃续跑变体是硬性验收方式 |
| E1–E6 的覆盖范围被误读 | §4.3 第 11 条写出检查工具的盲区；丢弃分支由场景测试约束 |
