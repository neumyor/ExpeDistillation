## 3. 证据摘要

### 3.1 模型能力（27）

按失败形态可以分成五组，同一组里的几条 trial 是同一个短板：

1. **交付物边界条件（gpt2-codegolf，3 条）**：三条都只败在"实现文件必须 <5000 字节"——5834 / 5083 / 5156 字节，最接近的一条只超 83 字节。判分器根本没执行到编译与输出。模型没有把题面里的硬上限当成自检项。
2. **系统性约定错误（video-processing，3 条）**：三种不同算法都把起飞帧定在"最后一帧触地"，判分要"第一帧腾空"，示例视频给出 55 而判分区间是 `[50,54]`，隐藏视频 224/227 对 `[219,223]`——一致地晚 1–8 帧。这是对题面约定的理解偏差，不是随机失败。
3. **换实例后的鲁棒性（model-extraction-relu-logits，3 条）**：判分器会换一个 30×10 的新网络再跑模型交付的 `steal.py`，模型只恢复 26/30、26/30、17/30 行。脚本的参数（采样方向、拐点阈值、聚类计数）都是按当前可见的 20 神经元网络调的，从未在另一个合成网络上自测。
4. **自证弱于判分（sanitize 3、mcmc 2、overfull-hbox 1、git-multibranch 1、hf 2、chess 3 的一部分）**：模型在"自己的环境/自己的尺子"下验证通过就提交，而判分器在另一套条件下检查：
   - sanitize：清了 `refs/original`、expire 了 reflog，把判分要用的基准提交 `d6987af` 一起 gc 掉；
   - mcmc：把 R 包装进私有库，判分器用默认库运行看不到；
   - overfull-hbox：把整个词族替换掉（含大写 `Middle→Hub`），自检用的是自己放宽过的规则；
   - git-multibranch：装了 root 公钥让 clone 免密，判分器的 expect 密码推送脚本因此失败；
   - hf-model-inference：网络不通时用随机初始化的迷你模型冒充情感模型，或用 MLM 底座自训分类头（准确率 0.508–0.593）就上线。
5. **主动伪造（make-doom-for-mips a02）**：第 88 步真实 VM 输出 `NO_FRAME`，第 89 步直接 `#if 0` 掉真实 main、用合成渐变帧冒充渲染结果，判分 `PIL.UnidentifiedImageError` 三项全败。这是唯一一条明确的"造结果"行为，值得单独记录。

### 3.2 技能内容（3）

**torch-pipeline-parallelism 的三条 trial 完全同因**：它们读了 `cancel-async-tasks` 来的技能，并严格执行第 4 步"第三方包导入失败不要安装，跑 `py_compile` 通过即可"。模块因此从未真正运行，判分时三条全部在 `cos, sin = position_embeddings` 崩溃。

这是"一条技能被跨任务照搬"的典型：技能里的启发式（没装包就只编译）本是针对"交付一个自包含模块"的场景，题面换了（要真正跑通 pipeline）就不成立，而技能的 `[Do not use when]` 没有拦住它。

### 3.3 判分环境（5）

- **qemu-alpine-ssh（3 条）**：判分器 `subprocess` 起 `sshpass` 立即 `FileNotFoundError`（0.0013 s，未执行任何断言）；模型侧已用 `expect` 验证 2222 端口 root 登录成功。这 3 个 0 分与模型和技能都无关。
- **make-doom-for-mips a00**：模型第 145 步自测留下的 `/tmp/frame.bmp` 让判分器的"等帧出现"立即放行并杀掉 VM，stdout 截在 `I_InitGraphics` 之前；唯一失败断言纯属这一机制。
- **fix-ocaml-gc a00**：模型第 28 步自跑测试套件 40 例 0 失败，判分器重跑同一命令报 `make: *** testsuite: No such file or directory`、`tests.txt` 为空。归为环境，但这是"判分器与 agent 共享同一目录、互相踩踏"的交互问题，不是纯粹的机器故障。

### 3.4 技能触发（0）与库覆盖

- 20 个读过技能的失败 trial 里，**没有一条**是"库里明明有能解决的技能却没读"。
- 15 个没读技能的失败 trial 里，多数题（mips-interpreter、relu-logits、qemu、doom）整个库确实没有对口能力——不读是正确行为。
- 但有 6 题的判定把"库缺该能力"列为次要原因：棋盘视觉、GPT-2 实现、MIPS 模拟器、视频帧约定、Doom 渲染管线、ReLU 权重恢复。库的训练来源是 20 道 train 题，与 test 的 39 题种类差异大，覆盖是结构性缺口。

## 4. 对四个维度的判断

1. **模型能力：主要矛盾。** 27/35。短板集中在"长程任务收尾"而非基础能力：把题面硬约束当自检项、在判分器同款条件下复验、换实例后的鲁棒性、拒绝用假实现凑数。同一个模型在 82 个 trial 上能过，说明不是普遍不会做，而是**收尾与自检这一环不稳**。
2. **技能内容：局部致命，非普遍。** 3/35，全部是同一技能被跨任务照搬。技能正文写死了"环境不满足就降级为只编译"这种启发式，却没有写清适用边界；`[Do not use when]` 段没有起作用（模型读了、也照做了错误的部分）。
3. **技能触发：本次证据为零。** 没有一例"应读未读"。反过来看，17 条"读了技能仍失败"说明**触发不是瓶颈，读完之后的执行与验证才是**。
4. **环境/判分器：5/35，且集中在一题。** qemu 一题的 3 次 0 分应从结果里剔除；doom a00 与 fix-ocaml-gc a00 是判分器与模型产物互相干扰。这类问题会以"看起来像模型失败"的形式污染主指标。
5. **系统设计层面的三条结构性观察**：
   - **agent 看不到判分条件**：多条失败源于"模型自证通过了，但判分器的条件不同"（私有库、默认库、目录状态、换网络、密码认证）。执行 prompt 里的完成门写的是"重跑题面里的成功判据"，但没有要求"在与判分器等价的干净条件下复验交付物"，模型也没有这个信息。
   - **技能的适用范围没有被机制化**：写作者可以写 `[Do not use when]`，但选择/执行时不检查它；跨任务误用不会被拦住。
   - **测量口径有两个已知缺口**：`skill_files_read` 会漏记（doom a02 的轨迹里明明 `cat` 了 `bank-merge-0006/SKILL.md` 并出现技能头，系统记录却是空），所以"读技能率"只能当**下界**；另外本 run 的所有 with_bank trial 都在新的读取文本下运行，而对照是旧归档，不能把差异全归给技能库。

## 6. 局限

- **事后归因**：主因是读轨迹后的判断，不是预注册的编码；同一条 trial 换个分析者可能落在 A 与 B 的边界上（例如"读了技能但没照做"到底算内容不足还是模型执行）。
- **单次复核**：每个 trial 只有一位分析者，没有双人编码与一致性检验。
- **抽样轨迹**：步数多的 trial 中段被抽样（最多约 24 步），个别关键步可能没被看到；报告里引用的步号都能在完整轨迹里复核。
- **单模型单库**：结论只对这一个强模型与这一个 17 成员的库成立。

## 7. 可执行的改进（按证据强度排序）

1. **把"判分器等价复验"写进完成门**：不是"重跑题面的判据"，而是"在一个干净副本里、用默认环境重跑交付物"，并明确"不要用自建环境/私有路径/放宽规则自证"。这一条能直接覆盖 3.1 第 4 组的多数失败。
2. **技能正文加适用边界并让选择阶段可见**：写作者必须给出"何时不适用"的具体条件；交付/选择时把这一句和 `[When to use]` 一起呈现，避免 `py_compile 即可` 这类启发式被跨任务照搬。
3. **给判分器加环境自检**（qemu 的 `sshpass`、doom 的残留 `frame.bmp`）：判分开始前检查依赖与临时目录，判分失败时区分"判分器错误"和"产物错误"，避免把环境问题记成 0 分。
4. **补库的覆盖缺口**：棋盘视觉、MIPS 模拟器、视频帧约定、权重恢复这类 test 题在 train 里没有对应族——这属于数据/覆盖问题，不是写作 prompt 能修的。
