# g49 作为实验宿主机

## 一、总体约定

- 所有实验只在 g49 上运行。本机（Mac）只做编辑、查看进度和提供出口隧道；node29 不再运行实验。
- g49 在清华内网，没有对外网络访问，DNS 也解析不了外网域名。要访问外部服务，一律走 Mac 提供的出口隧道（第二节）。
- 学生模型 Qwen3.6-35B-A3B 的服务：
  - ALFWorld：用 g49 本机的 vLLM（第三节）。
  - TB 2.1：智能体在 E2B 沙箱里调用模型，沙箱连不到 g49 的私网地址，所以走 llmcenter 网关。
  - SWE-bench：智能体（mini-SWE-agent）在 g49 上调用模型，只有 bash 命令在沙箱里执行，所以技术上能用 g49 的 vLLM；但对照是网关版 Qwen 的裸跑，为了同一来源比较，仍走 llmcenter 网关。
- 教师模型 DeepSeek 一律走 llmcenter 网关。从 g49 访问网关要用 `.co` 域名加出口隧道（`.cn` 域名经隧道会被网关的防火墙拦住，返回 418）。
- 目录（g49；`$EXPEDISTILL_HOME` 是实验根目录，写在 `expedistill.env` 里）：

| 路径 | 内容 |
|---|---|
| `$EXPEDISTILL_HOME/code/<提交>/` | 部署的代码，一个提交一个目录，不覆盖 |
| `$EXPEDISTILL_HOME/runs/<名>/` | run 目录 |
| `$EXPEDISTILL_HOME/expedistill.env` | 密钥与端点，权限 600，不进 git |
| `$EXPEDISTILL_HOME/ops/vllm/` | vLLM 服务的脚本、日志、pid 和 API 密钥文件 |
| `$EXPEDISTILL_HOME/tb/` | TB 的运行环境：`env/`（conda）、`venv/`（Harbor）、`scripts/`（runner 与 vendor）、`root/`（`EXPEDISTILL_TB_ROOT`） |
| `$HOME/swebench-eval/` | SWE-bench 评测环境，`.venv` 是指向 `.cenv`（conda 环境）的符号链接 |

## 二、Mac 出口隧道

Mac 上运行一个只放行 CONNECT 的代理（`scripts/remote/connect_proxy.py`），再用反向 ssh 隧道把它送到 g49 的 `127.0.0.1:18118`，断线自动重连。代理限制了目标域名（`modelbest.cn`、`modelbest.co`、`tencentags.com`，以及 pip 镜像 `tuna.tsinghua.edu.cn`、`pypi.org`、`pythonhosted.org`）。

```bash
# 在 Mac 上
TARGET_HOST=<g49 的 user@host> scripts/remote/egress_tunnel.sh start     # 启动代理和隧道循环（status、stop 同样要设 TARGET_HOST）
TARGET_HOST=... scripts/remote/egress_tunnel.sh status    # 代理、隧道循环是否存活，并从 g49 发一个真实请求
TARGET_HOST=... scripts/remote/egress_tunnel.sh stop
# 需要放行别的域名时：ALLOW="a.com b.com" TARGET_HOST=... scripts/remote/egress_tunnel.sh start
```

- Mac 睡眠、断网或重启后隧道会断，需要在 Mac 上重新 `start`；正在 g49 上跑的实验里，经隧道的请求会按各自的重试规则重试。长时间实验期间保持 Mac 不睡眠。
- g49 上凡是要访问外部的进程，环境里要有 `HTTPS_PROXY=http://127.0.0.1:18118`、`HTTP_PROXY=...`、`NO_PROXY=127.0.0.1,localhost`：
  - `expedistill.env` 已写入（驱动进程及其子进程继承）；
  - TB 的 runner 用干净环境启动，所以写在 runner 读取的 `tb/scripts/secrets.env` 里；
  - 手动运行 pip、conda 时自己 export。
- E2B 沙箱不能访问 Mac，也不能访问 g49，只能访问公网。

## 三、vLLM（Qwen3.6-35B-A3B）

三个 TP=2 的副本（GPU 0–5，端口 8110–8112，只监听 127.0.0.1），前面一个负载均衡（`scripts/remote/vllm_lb.py`，监听 `0.0.0.0:8010`，按在途请求数分配，流式响应保持时序）。对外仍是 `8010` 端口、模型名 `qwen3.6-35b-a3b`，需要 API 密钥（`ops/vllm/api_key`，权限 600）。GPU 6、7 留空。

```bash
cd $EXPEDISTILL_HOME/ops/vllm
mkdir -p run
export VLLM_ENV=<vLLM 0.32 的环境目录> \
       VLLM_MODEL_DIR=<Qwen3.6-35B-A3B 检查点目录> \
       VLLM_RUN_DIR=$PWD/run LB_LISTEN=0.0.0.0:8010 VLLM_API_KEY=$(cat api_key)
nohup setsid ./start_vllm_replicas.sh > run/start.log 2>&1 < /dev/null &    # 约 6 分钟
# 停止：VLLM_RUN_DIR=$PWD/run ./stop_vllm_replicas.sh
```

- 启动脚本先检查目标 GPU 都是空的，再逐个等副本 `/health`，最后发一个真实生成请求（问 6×21）才算就绪，失败时退出码非 0。
- 环境是 vLLM 0.32.0 的 conda 环境；这个模型的混合结构在别的版本上出过问题，不要换版本。
- ALFWorld 的执行温度在协议里固定为 0.95；vLLM 对没传的采样参数套用 checkpoint 的 generation_config（top_k 20、top_p 0.95）。
- `expedistill.env` 里通过 `EXPEDISTILL_LLM_ENDPOINTS` / `EXPEDISTILL_LLM_API_KEYS` / `EXPEDISTILL_LLM_MODEL_ALIASES` 把逻辑名 `qwen3.6-flash-distill` 映射到本机端点和实际模型名。

## 四、部署代码

```bash
# 在 Mac 上；设置文件放在仓库之外
cat ~/.expedistill/g49.deploy.env      # EXPEDISTILL_TB_HOST、_KEY、_DEPLOY_BASE、_REMOTE_PYTHON、_REMOTE_PROXY（用户、地址写在这里，不进仓库）
EXPEDISTILL_DEPLOY_ENV=$HOME/.expedistill/g49.deploy.env scripts/remote/deploy_bench_host.sh [--force]
```

- 远端 venv 用 uv 管理的 Python 3.11（包要求 3.9 到 3.11）；pip 经 Mac 隧道访问清华镜像。
- 部署后目录名是 `<提交>` 或 `<提交>-dirty-<时间戳>`，最后一行输出是远端的代码目录。

## 五、启动一次 run（三个 benchmark 通用）

```bash
cd $EXPEDISTILL_HOME/code/<提交>
EXPEDISTILL_ENV_FILE=$EXPEDISTILL_HOME/expedistill.env \
RUNS_DIR=$EXPEDISTILL_HOME/runs WORKERS=24 ROLLOUT_WORKERS=24 \
  scripts/remote/start_run_bench_host.sh <配置> [run 名] [其余参数]
```

续跑、supervisor、审计见 `scripts/remote/README.md`。`expedistill.env` 里 `EXPEDISTILL_TB_HOST=local`，表示驱动进程就在宿主机上。

### ALFWorld

- 评测环境：`$EXPEDISTILL_HOME/alfworld-eval`，用 alfworld-eval 目录里 `.venv` 的 Python 和数据（路径写在 `expedistill.env` 的 `EXPEDISTILL_ALFWORLD_VENV`、`ALFWORLD_DATA`）。
- 学生走本机 vLLM，教师走网关（经隧道）。
- 冒烟：`$EXPEDISTILL_HOME/tmp/alfworld_dryrun_g49_20261119.yaml`（3 个任务，七相位），run `alfworld_dryrun_g49_20261119_2220`。学生走本机 vLLM、教师走网关（经隧道），七个相位全部完成，退出码 0，`audit_run.py` 30 项 0 FAIL。

### SWE-bench

- 评测环境：`$HOME/swebench-eval`（conda 环境 `.cenv`；g49 是 CentOS 7，不能用 `uv sync`，见该目录 `docs/OPERATIONS.md` 第 15 节）。`.venv` 是指向 `.cenv` 的符号链接，因为插件固定调用 `.venv/bin/python scripts/run_unit.py`。
- `$HOME/swebench-eval/.env` 里的模型设置与 Mac 上的 `.env` 一致（学生 `qwen3.6-flash-distill`，网关 `.co`）；g49 专有的几项（`SKILLOPT_ROOT`、`TRACE2SKILL_ROOT`、`SWEBENCH_EMBEDDING_CACHE`、`HF_ENDPOINT`）保留。
- 子进程需要代理环境变量访问 E2B 和网关；驱动进程的环境里已有，手动运行时自己 export。
- 驱动进程需要 `EXPEDISTILL_SWEBENCH_ROOT=$HOME/swebench-eval`，写在运行的 `run.env` 里（先建 run 目录再写，启动脚本会读它）。
- 强模型执行者要求 `$HOME/swebench-eval/.env` 里有 `SWEBENCH_STRONG_MODEL=deepseek-v4-flash-0731--ali`（与配置里 `executor_strong` 的网关请求 ID 一致），`SWEBENCH_MAX_INFLIGHT=64`、`SWEBENCH_REFLECTOR_MAX_RPM=30` 与此前的正式运行一致。缺少 `SWEBENCH_STRONG_MODEL` 时桥接脚本会拒绝强模型单元。
- 冒烟 1（直接调桥接脚本）：`scripts/run_unit.py run --instance psf__requests-2931 --out runs/_support/g49_smoke_20261119 --model qwen3.6-flash-distill --max-input-tokens 131072`。结果：单元正常结束（`status final`，99 步，未解出），没有基础设施错误，说明沙箱创建、模型调用、判分整条链路在 g49 上通。
- 冒烟 2（经框架）：`$EXPEDISTILL_HOME/tmp/swebench_mini_g49_20261119.yaml`（每个划分一个任务，每个角色一次），run `swebench_mini_g49_20261119_2335`，只跑摸底相位：强模型（DeepSeek）单元完成，退出码 0。

### TB 2.1

- 环境：`tb/env` 是 conda Python 3.12，解释器用 patchelf 指向 glibc 2.28 的 sysroot（与 vLLM 环境同一做法，才能加载 manylinux_2_28 的轮子）；`tb/venv` 由它创建，里面装了 `vendor/requirements.txt` 和 Harbor 0.2.0（`vendor/claw-harbor`）。脚本：`scripts/remote/g49/setup_tb_env.sh`、`install_tb_harbor.sh`。
- runner 与 vendor 从 node29 上原来的 TB runner 目录复制到 `tb/scripts`，`tb/scripts/.venv` 是指向 `tb/venv` 的符号链接。runner 在 g49 的 bash 4.2 下有一处空数组展开报错，已改成兼容写法（原件保留为 `.orig_node29`）。
- `tb/root/env.sh`（模板见 `scripts/remote/g49/tb_root_env.sh`）：插件每次启动 runner 前读取，设置密钥、Harbor 的 Python 和可执行文件路径。`tb/scripts/secrets.env` 里有 E2B 与网关密钥、`OPENAI_API_KEY`（`TBENCH_LLM_KEY` 的别名）和代理变量。
- `expedistill.env` 里的 `EXPEDISTILL_TB_ROOT`、`EXPEDISTILL_TB_RUNNER`、`MODEL_API_BASE`、`TBENCH_*` 与 Mac 上的 `.env` 一致（路径改为 g49 的）。
- 冒烟 1（直接用 runner，一个任务）：`fix-git`，学生走网关，约 82 秒，奖励 1.0，没有错误。
- 冒烟 2（经框架）：`$EXPEDISTILL_HOME/tmp/tb_mini_g49_20261119.yaml`（`fix-git` 一个任务，每个角色一次），run `tb_mini_g49_20261119_2320b`，只跑摸底相位（`--until-phase 0`）：强、弱两个角色的单元都经插件、runner、Harbor 和沙箱完成，退出码 0。配置里的 `split` 与 `tasks` 必须一致（缩小配置时两处都改）。

## 六、已知限制

- Mac 的隧道是单点：Mac 睡眠、断网会让 g49 对外的请求全部失败。
- g49 上 DNS 不可用（每次解析约 56 秒后失败）；所有外部访问都显式走代理，由 Mac 解析域名。
- 沙箱里的模型请求只能走公网网关，不能用 g49 的 vLLM；如果以后需要，要在两边都能连到的位置建中继。
